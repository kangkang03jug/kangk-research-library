# ChatGPT Scheduled Task: daily research update

Run daily at the time and timezone defined in `config/research-profile.yaml` (for example, `08:00 Asia/Shanghai`). Use the connected GitHub repository as the source of truth. Read `prompts/daily-research-agent.md`, the Research Profile, all existing Paper Pool and user-state records, and today's daily archive before doing any work.

For Research Questions, explicit entries must use the configured explanation language in `question` and preserve the paper's verbatim wording in `original_question`; inferred entries must use only the explanation language in `question` and set `original_question` to `null`. Preserve a source locator and never invent an original wording.

Use Web Search and multiple reliable academic sources. Before writing Detail, actively retrieve and read public Full Text, Official HTML, or accessible PDF; Abstract + Metadata may draft Quick Read only. Do not stop at an abstract when full text is reasonably available. Set `reading_basis` to `full_text` or `official_html` only after covering Introduction/Motivation, Method, Experiments/Results, and Limitations/Discussion. Use `abstract_only` only after reasonable retrieval attempts fail and state that fallback in the record. Preserve Section/Page/Table/Figure locators. For every `full_text` or `official_html` paper, inspect Introduction/Motivation. Preserve every explicitly written RQ as `explicit`; if no explicit RQ exists but the authors' objective/core question can be reliably summarized, add at least one `inferred` question with a locator—do not leave `research_questions` empty merely because there is no `RQ1/RQ2`. Only leave it empty after reviewing the relevant sections and concluding that no reliable question can be extracted; then fill both `detail.research_questions_empty_reason` with a specific explanation and `detail.research_questions_empty_source` with the exact Introduction/Motivation locator. Set both to `null` whenever questions are present. Validation rejects missing, generic, or unlocated empty cases. Never present an inferred question as an original RQ number. Deduplicate first and process exactly one paper. If no new paper clears the quality bar, recommend an existing high-quality paper that is not Deep Read and has not already been recommended today. Preserve My Notes, My Tags, Deep Read, and Favorites. Generate all AI summaries and analysis in `language.explanation`; write 2–5 evidence-backed `detail.contributions` with locators where possible, and make `what_can_be_done_next` directly specific to the current paper's method, experiments, limitations, or follow-up tasks; the UI locale does not control paper-body language, and Original Abstract remains verbatim.

## Stable cloud execution and verification contract

This is a cloud Scheduled Task. Bind it to exactly the repository named in the task's connected GitHub context, normally `owner/repository` for this library, and do not read or write another Research Library. Confirm that the connection has `Contents: Read and write` permission before making changes. Never use a PAT, GitHub token, or OpenAI API key from a file or prompt.

Use this verification order:

1. Perform the in-task checks that do not require a local checkout: read the current `main`, confirm the Research Profile and today's archive, deduplicate by DOI/arXiv/OpenReview/title, preserve every `data/user` record, and validate the complete JSON shape against the checked-in schema and data-validation rules.
2. If this cloud task has a real repository workspace and can run `npm`, run `npm run validate:data`, relevant tests, and `npm run build` before committing.
3. If the cloud task only has the connected GitHub repository and cannot run local `npm` commands, do not abort solely for that reason and do not claim that local tests passed. Create one atomic commit on `main` through the authenticated GitHub connection. The repository's GitHub Actions CI and Pages workflow are the authoritative post-push validation gate.
4. After pushing, inspect both workflows until they finish. The Pages workflow's `validate:data` and production build, followed by Pages deployment, are the hard gate for the daily update. Inspect CI as well: if its failure is caused by this commit, make a focused repair commit and recheck Pages; if it is an unrelated pre-existing format/E2E baseline failure, report it separately and do not claim that CI is green, but do not block a Pages deployment that passed its own validation/build. Never describe a push as deployed while Pages validation/build or deployment is queued or failing.
5. If write permission is missing, read-only, requires approval, the target repository is ambiguous, or the push fails, make no data claim and report the exact limitation. Do not silently fall back to another repository.

For the local Codex CLI alternative, run the full checks before committing as documented in `docs/AUTOMATION.md`.

Detail depth: keep Quick Read as a short 1–3 minute orientation, but generate Detail as a substantial body-backed reading brief. Do not apply a single `concise` constraint to all Detail fields. For `full_text` / `official_html`, expand Motivation, Contributions, Research Questions, Method, Experiments & Key Findings, Limitations, Relation to Research, and follow-up directions with multiple paragraphs where useful. Explain the background, prior shortcomings, design choices, full input/output flow, datasets and baselines, key results and ablations, meaningful anomalies, concrete limitations, and profile-specific relevance. Keep author-reported limitations separate from AI analysis and preserve Section/Page/Table/Figure locators.

Serialize `detail.what_can_be_done_next` as an array of 3–6 paper-specific research directions. Each object must contain `title`, `rationale`, `concrete_plan`, `validation`, and `expected_value`, with optional `source`. Every direction must follow directly from this paper's method, experiments, limitations, transferable tasks, or stated questions; explain why it follows, how to execute it, how to test it, and what value it could add. Do not emit generic AI advice. Legacy string values remain readable for compatibility but new and edited records must use the structured array.

## 中文总结表达规范

当 `language.explanation = zh-CN` 时，所有 AI 生成的 Quick Read、Detail、Research Questions、Contributions、Limitations、Relation 和后续研究建议都必须以自然、简单、直观的中文为主。普通技术概念优先翻成中文；只保留方法名、模型名、数据集、指标、缩写和其他确实需要保留的专有名词。英文术语第一次出现时可写成“中文（英文）”，后文尽量只用中文，避免频繁中英文混写。

先解释“是什么意思”，再写必要的专业术语；多用短句，少用长句和术语堆叠。TL;DR 只写论文问题、核心方法、最重要结论和研究启发；“关键结果”只保留最重要的 1–3 个结论或代表性数字；“为什么重要 / AI 分析”必须写成容易理解、直接来自本文的研究启发，不能写成英文术语拼接或通用建议。生成后逐字段删除不必要的英文、重复术语、过长句子和没有解释的缩写；不得改写标题、作者、摘要、BibTeX、标识符、链接或 `original_question`。
